# Prompt 链 02 · 删除动效“看不见”的三轮追查

> 用途：第九届传智杯「AI创新应用挑战赛」提交材料 —— AI 协作过程快照（第 2 条）
> 对应提交：`6709602`（初版删除动效）→ `8a3eaa3`（弧线 + FLIP）→ `6ffc3a6`（让弧线真正看得见）→ `faedab6`（修掉 reduced-motion 快照）
> 时间：2026-10-15 23:57 → 2026-10-16 13:14

---

## 起点：删除只有 `window.confirm`

第一版的删除流程很直白：点「删除」→ 浏览器原生 `confirm` → 条目直接从 DOM 移除。没有警告样式，没有退出动画，也没有“删除后还能不能后悔”的区分。

---

## 第 1 轮：我只提了“要有动画 + 警告”

> **我的 Prompt（2026-10-15 23:57）：**
> 「当我要删除一条待办时要有动画跳出来，并且给出提示警告」

AI 把 `window.confirm` 换成了自定义确认弹窗（样式与界面一致）；确认后条目**先跳出去、动画播完才真正移除**。产物 `6709602`。

AI 当时的验收结论是“退出动画播完”。**我当时信了，但在真机上没看到。**

## 第 2 轮：“没有曲线删除啊”

12:46 我给了一张交互参考图，12:55 回「可以」。12:59 落了 `8a3eaa3`：删除从直线跳出改成弧线甩出，并给剩余条目加了 FLIP 让位、给标签加了抬起效果。

13:03，我在浏览器里删了一条，回复只有六个字：

> **我的 Prompt（2026-10-16 13:03）：**
> 「没有曲线删除啊」

AI 没有顺着我说“确实没有”，也没有直接重写。它先把动画冻结在 **0 / 60 / 120 / 180 / 240ms** 逐帧截图。

结论是：**动画是在跑的**——各帧都不同，条目在倾斜、上移、然后下落淡出。但我的感觉也是对的：**它看起来不像一条曲线**。

原因是两个很具体的量：

1. 这是一行约 1400px 宽的条目，位移只有 **38px（约 2.7%）**，肉眼基本无感。
2. 旋转是更糟的信号：在这么宽的行上转 2°，右端会被压下几十像素，看起来像“整行歪掉”，而不是曲线。

AI 自己否掉了第一版修法：加 `overflow: hidden` 裁剪 + 2° 旋转。它发现旋转太大，而且向上的弧会撞到上面的摘要文字。

第二版改成“向右滑出 + 下沉的弧”，并做了一次路径量化：

| t (ms) | dx | dy | dy/dx |
|---|---|---|---|
| 50 | 20 | 2 | 0.10 |
| 150 | 107 | 9 | 0.09 |
| 200 | 209 | 41 | 0.31 |
| 250 | 322 | 80 | 0.36 |
| 350 | 358 | 92 | ~0.25 |

> 「斜率从 0.09 升到 0.36 再回落——向右滑出的同时**后半程明显下坠**，是条实打实的弧。」

最终提交 `6ffc3a6` 把位移加到 **dx 420px / dy 165px**，旋转压到 **≤1.4°**，并让 `.listbox` 裁掉越界部分，读作“滑出列表”而不是“溢出页面”。commit 里的路径实测是斜率 **0.19 → 0.32** 递增。

### 这一轮的关键

AI 的第一反应不是“我再改一版”，而是**先测量**：逐帧截、量位移、量斜率。它先确认“动画在跑但读不出来”，再改参数。这个顺序很重要——如果它直接重写，最后可能只是换了一种同样看不见的动画。

## 第 3 轮：“其他动效好了，只有删除直接消失”

> **我的 Prompt（2026-10-16 13:12）：**
> 「刚把动画效果打开，可以看到动效了，但是删除还是直接消失」

这句话描述的是一个几乎不可能是巧合的组合：**别的动画都好了，只有删除立刻消失。**

AI 的判断：

> 「能看到其他动效但删除直接消失——这个组合很可疑。我怀疑 `REDUCE_MOTION` 在页面加载时被**快照**成了常量……CSS 媒体查询是实时的、所以其他动效正常了。」

关键是它说的下一句：**“先写个复现测试确认，不猜。”**

复现测试确认了故障：

- 点击删除瞬间，浏览器实时媒体查询是 `false`（**允许动画**）
- 但代码仍把条目立即移除（`itemsAt60ms: 3`、`leavingClassAt60ms: false`）

**根因代码：**

```js
const REDUCE_MOTION = window.matchMedia('(prefers-reduced-motion: reduce)').matches;  // ← 加载时快照
const ITEM_OUT_MS = REDUCE_MOTION ? 0 : 400;
```

| | 加载时 | 之后用户打开动画 | 结果 |
|---|---|---|---|
| CSS 媒体查询 | reduce | **实时变回 no-preference** | 其他动效恢复 ✓ |
| JS 常量 `REDUCE_MOTION` | `true` | **仍是 `true`**（永不更新） | 删除走“跳过动画”分支 → **瞬逝** ✗ |

**修复：**

```js
const reduceMQ = window.matchMedia('(prefers-reduced-motion: reduce)');
function prefersReduce() { return reduceMQ.matches; }   // 每次删除时现查，不再快照
const ITEM_OUT_MS = 400;
```

调用处：

```js
const reduce = prefersReduce();
itemEl.classList.add('item--leaving');
window.setTimeout(function () {
  const before = reduce ? null : captureTops();
  removeItem(id);
  if (before) animateLetWay(before);
}, reduce ? 0 : ITEM_OUT_MS);
```

**双场景验证：**

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 加载时 reduce → 之后打开动画（不刷新） | 直接消失 ✗ | 正常播放弧线 ✓ |
| 真实 reduce 环境 | 跳过 ✓ | 跳过 ✓（正确行为） |
| 正常环境 | 正常 ✓ | 正常 ✓，无残留 transform |

产物：commit `faedab6`，只改 `app.js`，+9/−4 行。

## 这条链证明了什么

**① AI 的“验收通过”不是验收。**
第一版它说动画播完了，我在真机上没看到。验收标准必须由用户在真实设备上执行；AI 的截图和 DOM 状态只能证明“代码跑了”，不能证明“人看见了”。

**② “没有”不是需求，是症状。**
我说“没有曲线删除啊”，AI 没有直接重写，而是先逐帧取证，确认“动画在跑但读不出来”，再改位移和旋转。先测量、再改参数，比“再改一版”可靠得多。

**③ 最有信息量的一句是反常事实。**
“其他动效都好了，只有删除不行”把搜索空间从“整套动画代码”压缩到了“这段代码和其他动效的差异”——那个差异就是加载时快照的常量。**我没有靠“还是不对”推进，而是靠提供一条反常的事实。**

**④ 修复被收在一行。**
没有重写动画，没有换库；只把加载时求值的常量改成调用时实时读取。最小修复让回归范围可控，也让“为什么修好了”能一句话说清。

**⑤ AI 主动承认第一版验收是错的。**
它没有把“看不见”归咎于用户设备、浏览器或缓存，而是先取证，再接受结论。这是这条链里最像“协作者”而不是“执行器”的地方。

### 看初版

打开 `../demo-del-v1/index.html`，删一条待办：能看到弹窗和跳出，但不是一条能读出来的弧线。

### 看弧线版

打开 `../demo-del/index.html`，正常环境删一条：能看到向右下滑出的弧线。

### 复现 reduced-motion 快照 bug

1. 打开 `../demo-del/index.html`
2. F12 → ⋮ → More tools → Rendering
3. 把 `Emulate CSS media feature prefers-reduced-motion` 设为 `reduce`
4. **刷新页面**
5. 把同一项切回 `no-preference`，**不要刷新**
6. 再删一条

预期：

- `6ffc3a6`（修复前）：条目**直接消失**，没有弧线
- 当前版本：正常播放弧线

**注意**：如果第 5 步之后刷新了页面，bug 就看不到了——这个 bug 的关键就是“页面在 reduce 下加载过，但之后没刷新”。

> 这条复现路径已在 Chrome headless 中实测：`6ffc3a6` 在点击后 60ms 条目已被移除、没有 `item--leaving`；当前版本在 60ms 时条目仍在、带 `item--leaving`，400ms 后才移除。
